# Experimental MCP transport

`o8d-mcp` serves `/api/mcp` only with both the `experimental-mcp` Cargo feature
and the `--experimental-mcp` runtime flag. The existing application and client
endpoints do not change automatically.

Build with:

```sh
cargo build --locked --manifest-path crates/o8d/Cargo.toml --features experimental-mcp
```

Start the TypeScript server with `O8D_MCP_READS=1`. Start the binary with an
explicit loopback `--listen` address and `--upstream` set to the current API base
resolved by the application. A listener port of zero asks the OS for a free port;
the first stdout line reports the selected listener. Point an opted-in MCP client
at that listener's `/api/mcp` URL.

This slice ports JSON-RPC handling and successful read-tool projections into Rust.
The protected TypeScript read APIs remain responsible for the shared SQLite state,
JSON registries, runtime/transcript observations, and lease reconciliation. Rust
does not independently open SQLite. The TypeScript process remains required.
There is no snapshot, alternate database, or response cache.

For each native request, Rust obtains current tool metadata with the opt-in
`o8d/read-context` method on the original `/api/mcp` endpoint. That request carries
the caller's credential and profile through the existing middleware. A refusal is
returned before reading any state. Server and requested profiles are intersected
by the existing TypeScript policy. Rust never loads or substitutes a bearer.

Rust handles `tools/list`, `o8_status`, `get_mission_status`, `o8_task_list`,
`o8_list_repos`, `o8_list_projects`, and `o8_lease_list`. The source routes are the
existing operator status/defaults, orchestrator status, task pool, repo/project,
and lease APIs. A failed read source falls back to its original TypeScript MCP
handler to preserve established error and retry policy. Tilde-path arguments also
retain TypeScript expansion. Initialization, other methods/tools, and any batch
containing a mutation are forwarded once with the original body bytes, caller
headers and upstream response, including session headers. HTTP hop-by-hop and
framing headers are regenerated by the HTTP client.

Both listener and upstream must be loopback. Upstream redirects are not followed.
If the upstream is unreachable, the transport returns a fixed 503 error. If the
TypeScript opt-in is absent, native requests fall back to the original endpoint.

## Parity and measurements

Run the real HTTP fixture suite with Node 22 and Rust stable:

```sh
npx vitest run tests/o8d-mcp-parity-real-path.test.ts tests/mcp-jsonrpc-parity.test.ts
```

The fixture uses the production middleware, MCP host, read APIs and persisted
lanes/projects/leases. Only external runtime/auth observations and screenshots
are fixture replacements. `tests/fixtures/mcp-parity/requests.json` records tool
calls, argument variants, profiles, batches, notifications and malformed input.
The fixture binds its generated repo path to `$FIXTURE_REPO`.

For two already-running opted-in listeners, set `O8_MCP_PARITY_TOKEN` in the
process environment and run:

```sh
node --import=tsx scripts/mcp-parity.ts --reference="$REFERENCE_API_BASE" --candidate="$CANDIDATE_API_BASE" --recording=tests/fixtures/mcp-parity/portable.json
```

The comparator checks status, protocol headers, JSON-RPC fields, array positions,
and JSON nested inside text content. Missing/extra fields fail. Valid timestamps
named `createdAt`, `updatedAt`, `decidedAt`, `generatedAt`, `checkedAt`, `observedAt`
or `timestamp` may differ; other freshness differences require exact JSON pointer
declarations in the recording. Only the documented freshness field names are
accepted. Types and field presence must still match. Mismatch reports include
field paths, without state values or credentials.

For reproducible latency numbers, build the optimized binary, set
`O8D_MCP_TEST_BINARY` to its absolute path and `O8_MCP_BENCH_REPORT` to a workspace
JSON output path, then run the real fixture suite. It interleaves both servers,
alternates their order, uses 10 warmups and 100 samples per tool, and calls the
same `rpc` client and `distribution` helper as `scripts/speed/mcp.mjs`. Reports
contain sample counts, p50 (`median`) and p95 milliseconds. These numbers include
the metadata/auth round trip and all source API calls. They describe the fixture
HTTP adapter, not a production Next.js process, and establish no speedup claim.
