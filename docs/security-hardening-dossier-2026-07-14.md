# o8 security hardening dossier — 2026-07-14

This review found two release-blocking trust failures and several high-impact boundary weaknesses. The PR fixes the exploitable paths it found, but it should remain a draft until the full web, native, relay, and license verification matrix is green and the residual risks below are accepted.

## Scope and method

The review followed data from every externally influenced entry point into a privileged sink: all App Router API routes, WebSocket and relay frames, the LLM tool bridge, filesystem helpers, HTML/SVG renderers, browser automation, Tauri capabilities and commands, license/invite endpoints, telemetry, provider-key storage, and all three JavaScript dependency trees. It also searched command-execution sites, DOM injection sinks, URL fetches, credential handling, route policy coverage, and the complete Git history with Gitleaks.

This is a source and local-build review, not a penetration test. It does not prove the security of Clerk, GitHub, Vercel, Apple Keychain, npm packages, Rust crates, hosted deployment policy, code signing infrastructure, or third-party binaries. The review standard follows OWASP's guidance to [deny authorization by default](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), validate all DNS answers and private address classes for [SSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html), sanitize untrusted markup before React DOM escape hatches under [XSS prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html), and bound public resource consumption under [API4:2023](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/).

## Findings and disposition

| Severity | Finding | Why it mattered | Disposition |
| --- | --- | --- | --- |
| Critical | LLM approvals were not bound to the exact tool call | A broad or reusable approval could authorize a different command or argument set after the human decision, turning the model into a confused deputy. Shell environment inheritance also exposed ambient provider credentials to approved commands. | Fixed with random, one-shot, server-side grants bound to tool name plus canonical arguments. Shell commands require an exact approval, secret-oriented commands remain blocked, and the child environment strips API keys, tokens, cookies, and cloud credentials. |
| Critical | Loopback transport was treated as operator identity | Any local browser origin, compromised renderer, same-host process, or relayed request that appeared local could reach privileged routes without proving an operator, worker, or paired-device principal. Query and unknown tokens could also collapse into trusted behavior. | Fixed with explicit `operator`, `worker`, `device`, and `anonymous` principals. The operator bearer is required even on loopback, worker/device tokens receive narrow method-and-path capabilities, unknown credentials fail closed, and only three read-only iframe resources retain socket-truth loopback access. |
| High | Workspace path checks were lexical only | A symlink inside an allowed repository could point outside it, so file reads and previews could disclose `~/.ssh`, cloud credentials, or other host files even when `..` was rejected. One preview route also accepted a caller-selected root. | Fixed with canonical root and existing-ancestor resolution, symlink and broken-link rejection, and registered-repository enforcement across operator docs, LLM files, context files, asset/content routes, and previews. Regression tests cover absolute paths, traversal, symlink escapes, and missing descendants. |
| High | Agent-controlled HTML and Mermaid SVG reached DOM injection sinks | Repository content, diffs, and generated explanations can be attacker-controlled. Unsanitized SVG/HTML can execute handlers, load remote resources, navigate the webview, or steal an operator bearer from the page. | Fixed by sanitizing every Mermaid sink, hardening full-document previews, sandboxing script-capable previews, disabling scripts in standalone blob tabs, and applying a CSP that blocks network resource classes, objects, and base-URL rewriting. |
| High | Browser automation and panel proxy could become SSRF and credential-forwarding deputies | An agent-controlled URL could target localhost, RFC1918, link-local, metadata, or o8's own API ports. The panel proxy also forwarded operator authorization, cookies, and o8 identity headers upstream. | Fixed with HTTP(S)-only URL parsing, credential rejection, IPv4/IPv6 private and metadata denial, validation of every A/AAAA answer, Playwright interception on every request and redirect, own-port denial, and removal of sensitive forwarding headers. |
| High | Provider keys were plaintext at rest and appeared in Google request URLs | The UI correctly redacted voice keys, but filesystem backups, local support bundles, malware, or another same-user process could read Groq, ElevenLabs, Gemini, OpenRouter, and Google TTS credentials. Query-string Google keys could also appear in proxy, error, or diagnostic URLs. | Fixed on macOS by storing provider secrets in Keychain, migrating legacy values on first use, removing them from JSON, returning only presence booleans to the webview, and constraining remaining preference-file permissions to `0600`. Google AI and TTS calls now authenticate with `x-goog-api-key` rather than URL parameters. The non-macOS residual is recorded below. |
| High | Relay resource limits were incomplete | Unbounded WebSocket frames, connection tracking, per-routing-ID rate buckets, and pending counters allowed cheap memory exhaustion and routing-ID rotation bypasses. | Fixed with a 1 MiB frame ceiling, disabled compression/client tracking, per-IP and global admission controls, bounded bucket cleanup, and pending-key deletion. Contract coverage includes rotating routing IDs. |
| High | Public license and invite flows were automation-friendly | Free-license issuance accepted unstable identities, invite codes had low entropy, redemption was non-atomic, and public resolve/redeem endpoints lacked layered throttling. Parallel requests could duplicate a single-use action. | Fixed with validated stable install IDs, per-install/IP/global rate limits, 128-bit invite codes, atomic local and central redemption, fail-closed Clerk authorized-party validation, and generic failure responses. Legacy invite codes remain accepted only for migration. |
| Medium | Crash reporting was enabled by default and scrub failure was fail-open | Error messages, stack frames, breadcrumbs, and repository-relative context may contain customer data. A sanitizer exception could previously allow an event to continue rather than be dropped. Feedback also attached a local crash digest unless the client explicitly declined. | Fixed by making reporting and feedback diagnostics opt-in, correcting the settings disclosure, dropping events on scrub failure, and testing hostile/throwing payloads. No raw environment, provider key, email, hostname, absolute home path, or cookie is intentionally transmitted. |
| Medium | Desktop CSP and capabilities were broader than use required | `unsafe-eval`, shell execution, and arbitrary child-webview creation increase the consequence of any renderer injection. | Fixed by removing `unsafe-eval`, adding `object-src` and `base-uri` restrictions, and removing unused shell-execute and create-webview permissions. A complete command-by-command Tauri ACL reduction remains in the residual register. |
| Medium | Known vulnerable transitive dependencies were present | Public advisories in the root, relay, and license trees create avoidable review failures even when the vulnerable path is not obviously reachable. | Fixed by upgrading Next.js, Sentry, Mermaid, `ws`, Hono, Drizzle, Postgres, esbuild, PostCSS, UUID, and related tooling while retaining the Clerk plugin version compatible with the app's Clerk major. All three npm audit trees report zero known vulnerabilities at review time. |
| Low | Secret scanning reported six historical heuristic matches | Security reviewers may interpret a red CI scan as leaked credentials even when the matches are identifiers or public protocol constants. | Triaged: current-tree matches are an environment-variable name and a sample idempotency key; the deleted-history match is Microsoft's public Edge read-aloud client constant. No user/provider credential was identified. The exact commit-scoped false positives are documented in `.gitleaksignore`, so a future value at the same source path still fails. |

## Trust boundaries after this PR

An API caller must now prove one of four identities, and each non-operator identity is a capability rather than a weaker operator token. The browser and relay remain untrusted transports. Agent-authored text remains untrusted even after a human chose the task. A filesystem path is authorized only after canonical containment. A human approval authorizes one canonical tool call, once. Provider keys stay in the provider request path and are excluded from telemetry, generated documents, shell children, API responses, and webview preference reads.

This is the security story reviewers should be able to verify in code. o8 does need broad local privileges to operate repositories and terminals, but those privileges are reached through explicit principals and narrow decision points rather than ambient localhost trust.

## Residual risk register

1. **High — same-user process isolation.** The operator bearer lives under the user's o8 data directory. Any malicious process already running as the same macOS account can read that file and act as the operator. Closing this requires an OS-backed broker or per-process sandbox/entitlement design; bearer hardening alone cannot create a privilege boundary within one Unix user.
2. **High — non-macOS voice secret storage.** macOS now uses Keychain. The current non-macOS compatibility path retains provider keys in a `0600` JSON file because Windows Credential Manager and Linux Secret Service are not integrated. Do not describe those platforms as encrypted-at-rest until that work lands.
3. **Medium — distributed abuse controls.** License rate limits are bounded and layered but in-memory per process. A multi-instance deployment needs a shared durable limiter at the edge or database layer, otherwise an attacker can distribute attempts across instances.
4. **Medium — DNS rebinding between validation and connection.** The browser engine validates the initial URL and every Playwright request, including all resolved A/AAAA answers, but Chromium performs its own later DNS resolution. Network egress policy or connection-level IP pinning is needed to eliminate that race completely.
5. **Medium — filesystem time-of-check/time-of-use.** Canonical containment defeats ordinary traversal and symlink escapes, but another same-user process can race a path after validation. Descriptor-relative `openat`-style access or OS sandboxing is required for a hard boundary against a malicious local peer.
6. **Medium — native invoke surface.** The removed Tauri permissions were unused and clearly excessive, but custom invoke commands still share a broad application webview trust domain. A future pass should map every command to the windows that need it and separate read, mutation, terminal, browser, and secret-bearing commands.
7. **Medium — public legacy invite format.** Central validation still accepts old six-digit invite codes so issued codes do not break. Rate limits and atomic redemption constrain abuse, but legacy codes should receive an expiry date and be removed after migration.
8. **Low — incomplete automated security tooling.** Dependency audits and Gitleaks were run, but the repository has no required SAST, Rust advisory audit, authenticated DAST, fuzzing, or SBOM/provenance gate. Those controls reduce recurrence; they do not replace the code-level fixes in this PR.

## Verification record

The branch includes focused regression suites for exact-call grants, principal authorization, route policy coverage, filesystem containment, HTML hardening, URL safety, proxy header stripping, telemetry scrubbing, relay admission, and license identity/invite behavior. The automated acceptance matrix is green:

- `npm run typecheck` passed.
- Changed-file ESLint passed with no errors; six unrelated advisory warnings remain in existing code.
- The full application suite passed: 277 files and 1,865 tests.
- Relay typecheck and contract tests passed.
- License-server typecheck, contract, and identity tests passed.
- `cargo check` passed after staging the generated speech sidecar, with six pre-existing warnings.
- Root, relay, and license `npm audit` each reported zero known vulnerabilities.
- The isolated Next.js 16.2.10 production build passed, including compilation, type analysis, static generation, and standalone tracing.
- Gitleaks scanned 4,750 commits and about 40.6 MB of Git content with the exact historical false positives recorded in `.gitleaksignore`; the resulting scan passed.

The remaining pre-merge verification is a human desktop smoke of operator authentication bootstrap and legacy voice-key migration into Keychain. This review does not guarantee that a credential never existed outside Git or in ignored files.

## Merge recommendation

Keep the PR draft until every acceptance gate above is green and a human reviews the authentication bootstrap, Keychain migration, browser URL policy, and exact-call approval UX. After that, merge this as a security boundary change with a release note that crash diagnostics are now opt-in and legacy voice keys migrate to macOS Keychain.
